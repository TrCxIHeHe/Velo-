Cybersecurity Architecture

Security — Mobile · API · Backend

Three attack surfaces, each defended independently. Compromise at one layer should not cascade to another.

Mobile Security
Storage & Runtime
  • Flutter Secure Storage — JWT tokens stored in Keychain (iOS) / Keystore (Android), never in SharedPreferences
  • Root / Jailbreak Detection — refuse to operate on compromised devices; use flutter_jailbreak_detection
  • App Integrity — Play Integrity API (Android) + DeviceCheck (iOS) to confirm genuine app binary
  • Memory Scrubbing — ride tokens cleared from memory immediately after use
Transport & Binding
  • SSL/TLS Certificate Pinning — app rejects connections to backend unless cert matches pinned hash; prevents MITM
  • Device Binding — ride tokens include device fingerprint; cannot be used from a different device even if stolen
  • Obfuscation — flutter build --obfuscate --split-debug-info for release builds
  • Secure deep links — verified App Links / Universal Links only, no custom scheme
API Security
Authentication Chain
  • Firebase Token → FastAPI verifies with Firebase Admin SDK on every request
  • JWT Access Token — 15 min expiry, signed with RS256 (asymmetric), stored in secure storage only
  • Refresh Token — 30 day expiry, single-use, rotated on each refresh (rotation prevents replay)
  • Ride Token — 30 sec expiry, HMAC-SHA256 signed, one-time flag in Redis; dock validates and immediately marks used
Request Defence
  • Rate Limiting — per-IP and per-user via Redis; login: 5 req/min, QR gen: 3 req/min, payment: 10 req/min
  • Replay Protection — each ride token has a jti (JWT ID) stored in Redis; duplicate jti = instant reject
  • QR Anti-Reuse — token marked used in Redis atomically with SETNX; race condition safe
  • Input Validation — Pydantic schemas on all FastAPI endpoints; no raw SQL, always ORM/parameterised
Backend & Infrastructure Security
Secret Management
  • No secrets in code or git — use .env + Docker secrets
  • Rotate Firebase service account keys quarterly
  • Razorpay webhook secret validated on every callback
  • DB password in environment variable only
Database Security
  • PostgreSQL encryption at rest (OS-level or pgcrypto)
  • Separate DB user per service (principle of least privilege)
  • Audit log table — every wallet debit, ride event, admin action
  • Daily automated pg_dump → MinIO with retention policy
Infrastructure
  • Cloudflare WAF + DDoS protection in front of all traffic
  • TLS 1.3 enforced everywhere; no HTTP allowed
  • Let's Encrypt cert auto-renewed via Coolify
  • SSH key-only access to VPS; password auth disabled
🔐
The most critical security item is QR anti-reuse. If a used ride token can be replayed, anyone can unlock scooters for free. The Redis SETNX (set-if-not-exists) atomic operation is the correct fix — not just checking a flag. Implement this before the first demo.
Database Architecture

PostgreSQL Schema — Core Tables

Ledger-based wallet, event-sourced rides, PostGIS for dock geometry. Every financial operation is append-only — no balance column, only transaction sum.

Core Table Overview

Why Ledger Model?
  • Auditability — every rupee movement has a record; disputes resolved with evidence
  • Fraud prevention — no balance column to tamper with; balance is computed, not stored
  • Refund integrity — refunds are credits, not updates; original debit still exists
  • Concurrency safe — balance check + debit in one DB transaction with row lock
💡
Add a PostgreSQL CHECK constraint on wallet_transactions to ensure amount > 0 always. The sign (debit vs credit) lives in the type enum, not the amount value. This prevents a class of bugs where a debit accidentally becomes a credit.
QR Security Architecture

Dynamic QR — 30s Expiry · JWT · One-Time Use

The QR is the most security-critical part of the entire product. A static QR or a reusable token lets anyone unlock scooters indefinitely. Here's the correct architecture.

QR Authentication Flow — Full
Generation (User Side)
User authenticated (Firebase token valid)
↓
User taps "Unlock" → POST /rides/token
↓
Backend generates ride token: { user_id, iat, exp: now+30s, jti: uuid4 }
↓
Token signed with HMAC-SHA256
↓
jti stored in Redis with 30s TTL
↓
Flutter encodes token → QR displayed
↓
Countdown timer shown (30 → 0s)
Validation (Dock Side)
ESP32 scanner reads QR code
↓
POST /docks/{id}/validate { token }
↓
Backend: verify HMAC signature
↓
Check exp — reject if expired
↓
SETNX jti:used in Redis → reject if exists
↓
Check wallet balance ≥ minimum
↓
200 OK → dock releases scooter
Security Properties
30s Expiry
Token expires in 30 seconds. A screenshot, screen recording, or stolen QR image is useless after 30s. The countdown timer on the Flutter screen communicates urgency to the user — regenerate before it hits 0.
One-Time Use (jti)
Each token has a unique jti (JWT ID). Redis SETNX marks it as used atomically on first scan. Any second scan of the same QR — even within 30s — is rejected. Prevents replay attacks.
HMAC Signature
Token is signed server-side. The dock (ESP32) cannot verify the token locally — it forwards to the backend API. Forged tokens fail HMAC verification. The signing secret never leaves the server.
QR Generation — What's in the Token
// JWT Payload (ride token)
{
  "sub": "user_abc123",       // user_id
  "jti": "uuid4-unique-per-qr", // one-time ID in Redis
  "iat": 1719200000,          // issued at
  "exp": 1719200030,          // issued at + 30s
  "did": "device_fingerprint"   // device binding
}
// Signed: HMAC-SHA256(payload, SERVER_SECRET)
⚡
For the MVP demo: the QR scanner on the dock is a dedicated 2D barcode reader module (e.g. GM65 or ZBar-compatible camera) connected to ESP32 via UART. The ESP32 simply reads the string and fires the POST request. It doesn't need to understand or verify the token — that's the backend's job.
