🧠 The Problem with One Chip

The original dock_controller.ino ran everything on the ESP32-CAM's single Xtensa LX6 core:

❌ Single-chip (old)
✅ Two-chip Option A (new)
Camera DMA
Competes with WiFi TX for bus
CAM core: DMA only, no contention
WiFi stack
~270 KB IRAM consumed on CAM
Runs on S3 (512 KB SRAM) instead
PSRAM
Needed for VGA framebuffer
GPIO12/13 freed → UART link to S3
Frame resolution
VGA (640×480) if PSRAM available
QVGA (320×240) — enough for QR, ~20 KB
HTTP POST latency
WiFi dropouts stall camera DMA
S3 handles retries independently
Solenoid driver
On CAM GPIO12 (PSRAM conflict)
Clean GPIO10 on S3, no conflicts
Serial debug
Only UART0 — same as FTDI port
S3 has native USB CDC — plug & go
Bottom line: The CAM's LX6 core can DMA-capture a QVGA JPEG in ~40 ms. With WiFi running, that same frame takes 200–600 ms because DMA, WiFi TX and the TCP stack all fight for the same AHB bus. Removing WiFi from the CAM entirely eliminates that fight and makes capture times stable and fast.
💡 Why the ESP32-S3 Specifically

S3 advantages for the gateway role

  • Dual-core Xtensa LX7 — one core for UART receive, one for WiFi TX
  • Native USB CDC — no FTDI needed, appears as COM port immediately
  • 512 KB SRAM — fits a 200 KB frame buffer with room to spare
  • Better WiFi PHY — 802.11b/g/n, antenna diversity on most dev boards
  • GPIO10 free — clean solenoid driver pin, no peripheral conflicts

CAM kept lean on purpose

  • Zero WiFi code — WiFi.h not even included in cam_firmware.ino
  • One job only: capture JPEG → write to Serial2 → wait for ACK
  • QVGA in DRAM — no PSRAM dependency, fewer init failure modes
  • 3× retry on FAIL — tries fresh captures before giving up
  • LED blink on success so you can see it working without a laptop

🖥 router.py — what changed and why

B-03 — MAX_IMAGE_BYTES

Old: 5 MB. A real OV2640 VGA frame is 40–80 KB. Allowing 5 MB means 60–250× more numpy/malloc work on any junk payload. Fixed to 200 KB.

B-04 — Audit logging

AuditLogRepository was imported but never instantiated. Every scan attempt (success, QR fail, confirm fail) now writes an audit row so you can monitor false-scan rates in production.

B-05 — Rate limiting

No rate limit on the scan endpoint = trivial DoS. Added @limiter.limit("20/minute"). The S3 scans at ~2/min at most; 20 blocks abuse while leaving real headroom.

B-06 — Content-Type guard

Any Content-Type was accepted. Now rejects non-image bodies with 415 at the HTTP layer, before the image is read or decoded. Also added a MIN_IMAGE_BYTES (1 KB) guard for sub-frame noise.
🔬 service.py — what changed and why
1
Size normalisation (_normalise_size)
OV2640 can send frames from 160×120 to 1600×1200 depending on firmware settings. cv2.QRCodeDetector works best at ~640 px wide. Frames wider than 800 px are downscaled; frames narrower than 200 px are upscaled to 640×480.
2
GaussianBlur → adaptiveThreshold (_preprocess_for_qr)
Raw OV2640 JPEGs have JPEG compression artefacts (ringing, blockiness) around the QR module edges. GaussianBlur(3×3) removes noise before thresholding. adaptiveThreshold normalises uneven dock lighting — a phone screen held at an angle under a bright LED is a classic failure mode this fixes.
3
pyzbar 4-pass fallback
cv2.QRCodeDetector is fast but poor on rotated, blurry or compressed-twice frames. pyzbar (ZBar library) handles all of those. The pipeline runs: cv2 raw → cv2 enhanced → pyzbar raw → pyzbar enhanced. Cheapest first; stops as soon as any pass succeeds.
🚫
Never power the ESP32-CAM from the FTDI 3.3V or 5V pin during operation. The OV2640 draws 150–250 mA peak. FTDI regulators are rated 50 mA and will brown-out the camera mid-frame. Use the external 5V PSU for power; FTDI only carries TX/RX/GND for programming.

📡 UART Link — ESP32-CAM ↔ ESP32-S3 921600 baud · always connected
ESP32-CAM PinDirectionESP32-S3 PinSignal
GPIO12 (TX) ──────▶ GPIO18 (RX) Frame data — 4-byte header + JPEG body
GPIO13 (RX) ◀────── GPIO17 (TX) ACK byte — 0x4F (OK) or 0x46 (FAIL)
GND ──────── GND Shared ground rail — required for UART signal reference
Why GPIO12/13 on the CAM? These are the PSRAM SPI pins (MTDI/MTCK) on AI Thinker. Repurposing them means psramFound() returns false → camera falls back to QVGA in DRAM. That's fine — QVGA at quality 12 is ~20 KB, well within the 200 KB backend limit and transmits over UART in ~0.2 s. If you ever need VGA + PSRAM simultaneously, rewire to GPIO14/GPIO15 on the CAM and update S3_UART_TX_PIN / S3_UART_RX_PIN in cam_firmware.ino + CAM_UART_RX_PIN / CAM_UART_TX_PIN in s3_gateway.ino.
🔒 Solenoid Circuit — ESP32-S3 GPIO10 → MOSFET → Solenoid
ComponentConnectionNotes
GPIO10 → MOSFET Gate (via 100Ω resistor) Logic-level N-MOSFET (e.g. IRLZ44N). 100Ω limits gate current during switching.
MOSFET Drain → Solenoid − Drain sinks current through solenoid coil
Solenoid + → 12V supply + Coil + always connected to 12V
Flyback diode Cathode → 12V, Anode → Drain Required. Solenoid is an inductor — de-energising generates a voltage spike that kills the MOSFET without this (1N4007 works).
MOSFET Source → Shared GND rail Must share GND with S3 and CAM
Gate pull-down 10 kΩ from Gate to GND Holds gate LOW during S3 boot so solenoid doesn't fire on startup
📡 CAM → S3 Frame Protocol

The protocol is intentionally minimal — no framing overhead, no checksums. UART at 921600 baud over a 10 cm wire is reliable; checksums add code complexity with essentially zero real benefit at this distance.

CAM → S3
byte 0 byte 1 byte 2 byte 3 ← big-endian uint32 frame length → byte 0 byte 1 … byte N ← raw JPEG body (N bytes) →
S3 → CAM
0x4F 'O' ACK OK — ride confirmed, solenoid fired or 0x46 'F' ACK FAIL — QR not decoded or backend error
Why big-endian uint32 header? The S3 reads exactly 4 bytes, reassembles the length with bit-shifts, then calls Serial1.readBytes(buf, length) exactly once. No delimiter scanning, no state machine — the receiver always knows precisely how many bytes to wait for.
Why 921600 baud? A 20 KB QVGA frame at 921600 baud (≈ 92 KB/s) takes ~0.22 s. At 115200 baud it would take 1.74 s — too slow for a responsive unlock. 921600 is a standard ESP32 UART speed; 1 Mbaud and above needs clock tuning and is unreliable at 3.3V over >30 cm wires.
Why send ACK before solenoid? triggerSolenoid() blocks for 3000 ms. Sending the ACK byte first lets the CAM enter its 3 s cooldown immediately and in parallel, so the next scan cycle is ready the moment the solenoid closes — no extra latency.
⏱ Timing Budget (QVGA, quality 12)
StageTypical timeNotes

🔄 Retry Logic
CAM S3 │ │ ├─ capture frame ─────────────────────────────────▶ │ ├─ send header + JPEG ────────────────────────────▶ │ │ POST to backend │ backend returns 422 (QR not found) │◀─────────────────────── ACK_FAIL (0x46) ──────────┤ │ ├─ [attempt 2] capture fresh frame ───────────────▶ │ ├─ send header + JPEG ────────────────────────────▶ │ │ backend returns 200 │◀─────────────────────── ACK_OK (0x4F) ────────────┤ │ │── GPIO10 HIGH → solenoid │ LED blink ×3 │── delay 3000 ms │ cool-down delay 3s │── GPIO10 LOW
409 / 410 (token expired or reused): S3 sends FAIL but CAM will still exhaust its 3 retries and back off. A new token must be generated in the app. There's no special fast-exit path on the CAM side because it doesn't understand HTTP status codes — only OK/FAIL.

💡
Flash order doesn't matter — each chip boots independently. The CAM will just send frames into the void until the S3 is up and ready to receive. The S3 will sit in receiveFrame() with a 30 s header timeout, looping harmlessly until the CAM starts sending.

Generates a test_qr_generated.png → POSTs it to the backend → ride should activate. 200 + "✅ Ride activated!" means the full backend pipeline works.
4
Test with a real QR image from the Flutter app
# Screenshot the QR unlock screen → save as qr.png
python test_scan.py \
  --host 192.168.1.X \
  --dock YOUR_DOCK_UUID \
  --image qr.png
Use this to verify that pyzbar can decode a phone-screenshot QR at various sizes and qualities before the ESP32-CAM hardware is involved.
5
Monitor S3 serial output live
